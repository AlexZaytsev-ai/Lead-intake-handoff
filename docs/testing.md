# Проверки

## Пройдено в исходной среде

| Сценарий | Наблюдаемый результат |
| --- | --- |
| Бюджет «пока не знаю» | Сбор продолжился без повторного обязательного вопроса о бюджете |
| Все данные и имя одним сообщением | Правильная сводка и подтверждение передачи |
| Просьба менеджера до анкеты | Передача с `client_requested`, отсутствующие сведения показаны как неуказанные |
| Отказ «Не хочу называть имя» после вопроса об имени | После исправления: `client_name = null`, `unknown_fields` содержит `client_name`, передача `sent` |
| Дополнение после передачи | Сообщение в группе, подтверждение клиенту; используется собранное имя с fallback на профиль |
| Команда из группы | IF отправил событие в False до сохранения заявки |
| Поиск «договор» | Найден фрагмент о договоре и дополнительные совпадения |
| Вопрос о договоре при сборе | Ответ по знаниям, затем вопрос о площади |
| Площадь и вопрос об ипотеке | Площадь учтена, информации об ипотеке не найдено, затем вопрос о городе |
| Остальные данные и вопрос о гарантии | Ответ о 12 месяцах, правильная сводка с площадью 48 м² и бюджетом 700 000 ₽ |
| Итог передачи с RAG | `leads.status = handed_off`, `handoffs.status = sent`, оба Telegram ID заполнены, исходное сообщение `done` |
| Имитация sent + collecting | Отдельная нода мониторинга вернула тестовую заявку в `handed_off` |
| Имитация зависшего входящего сообщения | Предупреждение содержало статус передачи и оба ID отправок; тестовая запись возвращена в `done` |

Изменённая формулировка «Этот вопрос лучше уточнить у менеджера» добавлена в финальный экспорт после теста отсутствия знаний. Отдельный повторный тест этой формулировки в Telegram не зафиксирован.

## Приёмка после импорта

На новом тестовом чате:

1. «Нужен косметический ремонт квартиры. Вы работаете по договору?» → ответ про договор, затем вопрос о площади.
2. «48 м². Можно оплатить ремонт ипотекой?» → без выдуманных условий оплаты, затем вопрос о городе.
3. «Квартира в Санкт-Петербурге. Начать хочу через месяц, бюджет 700 тысяч рублей. Меня зовут Алексей. Какая гарантия на работы?» → ответ про гарантию, сводка в группе, подтверждение клиенту.
4. «Ещё нужен демонтаж обоев» → дополнение в группе и подтверждение клиенту.
5. В БД проверить итог ниже. Последующие сообщения должны отдельно завершаться `done`.

```sql
SELECT l.id, l.status AS lead_status,
       h.status AS handoff_status,
       h.telegram_message_id, h.client_confirmation_message_id,
       m.processing_status
FROM leads l
JOIN handoffs h ON h.lead_id = l.id
LEFT JOIN messages m ON m.id = h.source_message_id
WHERE l.chat_id = <TEST_CLIENT_CHAT_ID>;
```

Заменить `<TEST_CLIENT_CHAT_ID>` числом. Эта выборка только читает БД.

## Что пока не подтверждено

- Повторная доставка одного и того же Telegram update: защита есть в SQL и IF, но отдельный контролируемый повтор update в текущем прогоне не зафиксирован. Повтор текста обычным сообщением создаёт другой Telegram message ID и не является этим тестом.
- Фактическое отключение PostgreSQL и срабатывание трёх попыток.
- Тайм-аут Telegram после доставки, восстановление по message ID из execution.
- Блокировка бота клиентом, голосовые, фото, длинные сообщения, некорректные числовые значения, prompt injection и нагрузка.
- Импорт очищенных workflow и запуск SQL с нуля в отдельной среде.

Не менять `chat_id` у реальных клиентов ради теста. В разработке использовались фиктивные ID для сохранения истории; их очистка и сверка с исходными execution — отдельная задача. Новые тесты лучше выполнять в отдельной БД с отдельным ботом.
