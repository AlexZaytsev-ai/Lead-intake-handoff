# Lead Intake & Handoff

Демонстрационный Telegram-бот для приёма заявок на ремонт квартир. Собирает данные в диалоге, отвечает на вопросы об условиях компании и отправляет сводку в общий чат менеджеров.

Компания и её условия вымышленные. Проект показывает интеграцию Telegram, n8n, PostgreSQL и AI-модели; это рабочее демо, не готовый сервис для клиентов.

## Что умеет

- Сохраняет заявку и входящее текстовое сообщение до обращения к модели.
- Извлекает тип ремонта, площадь, город, сроки, бюджет и имя через Structured Output Parser.
- Задаёт недостающие вопросы, учитывает проверенные ответы «пока не знаю» и отказ назвать имя.
- Передаёт заявку по просьбе клиента или после заполнения либо явного пропуска полей.
- Отправляет сводку в группу и подтверждение клиенту, сохраняет ID этих сообщений.
- После передачи направляет новые сообщения клиента в группу.
- Отвечает по небольшой базе условий компании через RAG с полнотекстовым поиском PostgreSQL.
- Отдельно отслеживает зависшие сообщения и передачи, восстанавливает один вид несогласованности статусов.

## Стек

n8n, Telegram Bot API, PostgreSQL, JavaScript, OpenAI Chat Model, Structured Output Parser. В экспорте выбрана модель `gpt-4.1`. Для RAG используются `to_tsvector`, `plainto_tsquery` и русская конфигурация поиска. pgvector и embeddings не используются.

## Как проходит заявка

1. Фильтр пропускает сообщения из личных чатов.
2. SQL создаёт или обновляет заявку и сохраняет входящее сообщение. Повторный Telegram message ID для той же заявки отсекается уникальным ограничением.
3. AI извлекает только данные текущего сообщения. SQL объединяет их с уже собранной заявкой.
4. Если есть вопрос об условиях, AI выделяет поисковую тему; PostgreSQL возвращает до трёх фрагментов, другая AI-цепочка формирует ответ. После него продолжается анкета.
5. JavaScript выбирает следующий вопрос либо передачу менеджеру. При явной просьбе сотрудника анкета не обязательна.
6. В базе создаётся передача `pending`. После успешной отправки сводки сохраняются `sent` и Telegram message ID.
7. Заявка получает `handed_off`. После подтверждения клиенту сохраняется ID подтверждения, исходное сообщение получает `done`.

## Ограничения

- Один Telegram-чат соответствует одной заявке (`UNIQUE chat_id`). Новая заявка того же клиента и закрытие старой не реализованы. Фиктивные chat ID использовались только при разработке, не являются пользовательским сценарием.
- Работа двух менеджеров реализована как общий чат. Назначения ответственного, round-robin и ответа клиенту из группы нет.
- RAG включён только во время сбора заявки. После передачи все сообщения, включая вопросы, направляются менеджерам.
- Поиск лексический: модель преобразует вопрос в ключевое слово или тему. Ошибки классификации, синонимы и вопросы на несколько тем могут ухудшить результат. Оценка качества на большом наборе вопросов не проведена.
- Неизвестные поля отмечаются текущей реализацией по ограниченному набору регулярных выражений. Массив `unknown_fields`, возвращённый AI, в сохранении пропусков сейчас не используется.
- Нет гарантии доставки ровно один раз. Тайм-аут Telegram оставляет неопределённость: сообщение могло дойти.
- Повтор того же входящего сообщения блокируется даже после сбоя. `INSERT ... DO NOTHING` для уже существующей передачи не продолжает её обработку.
- Автоматической повторной отправки нет. Мониторинг предупреждает, а спорные отправки требуют ручной проверки.
- ID исходящих уточняющих вопросов и последующих сообщений менеджеру не сохраняются как отдельные исходящие записи `messages`; ID первичной сводки и подтверждения хранятся в `handoffs`.
- Вопросы без ответа не добавляются отдельно в сводку менеджеру: исходный текст сохраняется в `messages`.
- Голосовые сообщения, фото и вложения не поддержаны. Входной фильтр проверяет тип чата, но не наличие текста; такие сообщения могут завершиться ошибкой сохранения.
- Защита от гонок параллельных сообщений, нагрузочная проверка и полная защита от prompt injection не реализованы/не проверены.

## Состояние проверки

В исходной среде пройдены диалог, передача, последующие сообщения, пропуск бюджета, отказ назвать имя и RAG. Итоговый тест завершился статусами `handed_off`, `sent`, `done` и сохранёнными ID отправок.

Публичные копии очищены от привязок credentials, webhook ID, внутренних ID workflow, адресов чатов и отдельных тестовых SQL-нод. Рабочая логика сохранена. Импорт очищенных копий в чистый n8n и развёртывание приложенного SQL в PostgreSQL в ходе подготовки архива не выполнялись. Точные версии исходного окружения перед повторным развёртыванием следует зафиксировать.
