# Сбои и восстановление

## Что автоматизировано

В основном workflow три попытки записи в базу с интервалом в секунду настроены для сохранения отправленной передачи, обновления статуса заявки и фиксации подтверждения клиенту. Это повторы SQL, а не Telegram-отправки. Фактический отказ базы для проверки этих попыток ещё не моделировали.

Мониторинг находит входящие сообщения `pending` и передачи `pending` старше 5 минут. После успешного предупреждения запоминает его время; повторное предупреждение допускается через час.

Отдельная ветка исправляет `collecting` на `handed_off`, если в `handoffs` уже есть `sent`, Telegram message ID и `sent_at` старше 5 минут. Это проверено на искусственно изменённой тестовой записи. Эта ветка не отправляет подтверждение клиенту и не завершает входящее сообщение.

## Как принимать решение

| Ситуация | Действие |
| --- | --- |
| Telegram-нода успешна, последующая запись в БД упала | Взять message ID и время из успешного Output того же execution. Восстановить запись в БД, не посылать сводку повторно |
| Тайм-аут Telegram, успешного результата нет | Проверить целевой чат и execution. Пустой ID в БД не доказывает отсутствие доставки |
| В handoffs sent, в leads collecting | Мониторинг исправит статус при выполнении условий; отдельно проверить подтверждение клиенту |
| Сводка сохранена, подтверждение не зафиксировано | Проверить execution ноды «Подтвердить клиенту». Если отправка успешна, восстановить её ID; если статус доставки неясен, не повторять слепо |
| Первичная AI-обработка упала | Проверить execution. Повтор того же входящего update отсекается; автоматического продолжения этого пути нет |

При сверке идентифицировать не только message ID, но и чат: Telegram message ID имеет смысл в пределах конкретного чата.

## Шаблон восстановления записи о сводке

Не запускать без заполнения всех параметров из одного подтверждённого execution. Query Parameters: `[handoff_id, message_id, unix_date, manager_chat_id]`.

```sql
UPDATE handoffs
SET status = 'sent',
    telegram_message_id = $2::bigint,
    sent_at = to_timestamp($3::double precision),
    last_error = NULL
WHERE id = $1::bigint
  AND manager_chat_id = $4::bigint
  AND status = 'pending'
  AND telegram_message_id IS NULL
RETURNING id, lead_id, status, telegram_message_id;
```

Это шаблон, разобранный по успешному Output, а не автоматически протестированный механизм восстановления. Он не обновляет `leads`, не подтверждает передачу клиенту и не ставит `messages.done`. После него нужно отдельно сверить эти этапы. При пустом результате сначала проверить условия и текущие данные.

## Почему нет слепого повтора

Отправка Telegram и запись PostgreSQL не являются одной транзакцией. Telegram может доставить сообщение, а n8n не получить ответ или не успеть записать его. Уникальность `(lead_id, manager_chat_id)` предотвращает вторую запись передачи, но не вторую внешнюю отправку.

`ON CONFLICT DO NOTHING` сейчас останавливает путь при уже существующей передаче. Это защита от повторного создания, а не очередь повторной доставки. Полноценный delivery worker, блокировки конкурентных обработчиков, журнал попыток и политика обработки неопределённых отправок остаются дальнейшим развитием.
